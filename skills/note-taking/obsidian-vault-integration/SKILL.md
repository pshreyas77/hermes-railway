# Obsidian Vault Integration — Second-Brain Wiring

Use this skill AFTER creating a substantive note with the `obsidian` skill. The `obsidian` skill handles file I/O; this skill handles integration into the vault's MOC/index/backlink fabric.

**Trigger:** A new research note, synthesis note, or presentation artifact (HTML slideshow, markdown slides, etc.) was just created. The note exists on disk but is not yet wired into the vault's graph.

**User rule: ALL work on E: drive. Never use C: for tool installs, source code, or project files. Shrey's vault is at `/vault` (cloned from GitHub on startup).**

**Factual claims in notes: ALWAYS cross-check against Wikipedia before storing.** The user explicitly requires verification of elections, biographies, institutional affiliations, dates, and numbers before they enter the vault. Claims that were not cross-checked will be challenged. For any time-sensitive claim (elections, current events), verify the current date and check if the event already happened.

**When to use:** Substantive notes that link to 3+ existing notes, or notes the user explicitly asked to be "stored and linked." Skip for trivial one-off notes (quick capture, scratch files, daily logs).

## Step 1: Add to the immediate parent MOC

Find `00_<topic>_MOC.md` in the note's parent folder (or one level up if no local MOC). Add the new note to its file listing. Bump `Files:` count and `Updated:` date.

## Step 2: Trace upward to area-level MOCs

Check the parent folder and area root for:
- Area-level `00_<Area>_MOC.md` — these list topic-cluster MOCs in a `## 📂 Topic Clusters` section
- `00_FILE_INDEX.md` — alphabetical index (DO NOT edit if footer says "Auto-generated by Topic Organizer")
- `00_TOPICS_MASTER_INDEX.md` or vault-wide `index.md`

Confirm the chain `Master Index → Area MOC → Topic MOC → New Note` is navigable. Most well-organized vaults already have the topic MOC linked from the area MOC, so the chain works as soon as the topic MOC references the new note.

## Step 3: Add back-references to all related notes

Every note referenced via `[[wikilinks]]` in the new note should receive a reciprocal back-reference entry.

### Approach

1. List the notes linked from the new note's `Related Notes` / `Related Vault Notes` section
2. Read the tail of each (~last 20–30 lines) to find existing `Related Notes` or `Related Files in Vault` sections
3. Patch in a one-line back-reference with brief context

### Format

```markdown
- [[New Note Title]] — One-line description of connection and relevance
```

Keep it to one line per back-reference. The goal is graph navigation, not duplication.

### If a note lacks a `Related Notes` section

Append one after the last substantive section:

```markdown
---

## Related Notes (Backlinks)
- [[New Note Title]] — Brief context
```

### Common section names to patch into

- `## Related Notes` (most common)
- `## Related Files in Vault`
- `## Related`
- `## 🔗 Related Topics`

## Step 4: Verify the wiring

```bash
grep -c "New Note Title" "path/to/parent_MOC.md"
grep -c "New Note Title" "path/to/related_note_1.md"
# … one per linked note
```

Each should return `1` or higher. If `0`, the patch didn't apply — re-read the file and retry.

## Vault Structure Conventions

### PARA/Zettelkasten-style vault
- `00 - SYSTEM/` — vault config, dashboard
- `01 - PROJECTS/` / `03 - PROJECTS/` — active projects
- `02 - AREAS/` — areas of responsibility, each with subfolders + MOCs
- `03 - RESOURCES/` — reference material
- `04 - DAILY/` — daily notes
- `05 - MAPS/` — Maps of Content
- `0-raw/`, `1-desk/`, `2-atoms/`, `3-threads/` — atomic notes pipeline

### MOC file naming
- Topic MOCs: `00_<topic>_MOC.md` in the note's folder or one level up
- Area MOCs: `00_<Area>_MOC.md` in the area root
- Vault master: `00_TOPICS_MASTER_INDEX.md` or `index.md`

### Files to NOT manually edit
- `.smart-env/multi/*.ajson` — AI-compiled summaries
- `00_FILE_INDEX.md` with footer `*Auto-generated by Topic Organizer*`
- `GRAPHIFY KNOWLEDGE GRAPH` and similar generated dashboards

## Generating Obsidian Canvas Files

A `.canvas` file is JSON: `{"nodes":[], "edges":[], "metadata":{"version":"1.0-1.0","frontmatter":{}}}`. Each node needs `id`, `type`, `x`, `y`, `width`, `height`, and `text` (HTML for `type:"text"`). Edges connect nodes via `fromNode`/`toNode`.

**When to generate canvases programmatically:**
- Flashcard decks from catalog notes (book library, topic reviews)
- Visual dashboards from structured metadata (reading progress, project boards)
- Any grid-layout artifact derived from many vault notes

**Script workflow:**
1. `os.listdir()` on the notes folder — no tool path issues with glob patterns
2. Regex-frontmatter parse: `re.match(r"^---\n(.*?)\n---", raw, re.DOTALL)` on each `.md` file
3. Classify by combining `genre` (lower-cased) + `tags` + title keywords — all in one lowercase string
4. Compute x/y from col/row indices: `x = START_X + col * (CARD_W + PAD_X)`
5. Build HTML text content for each node (covers, takeaways, badges, ratings)
6. `json.dump()` the canvas, write with `write_file`

**Classification ordering matters:** check specific title-sets (e.g. banned-book titles) before broad keyword matches (e.g. "fiction"), since one title can match multiple classifiers.

**Cover image priority:** local `file:///` paths for manually saved covers > OpenLibrary URLs from frontmatter `cover:` field. Match local covers by slug-comparing note filename to cover filename.

**Key takeaways regex:**
```python
kt_match = re.search(r"## Key Takeaways\s*\n(.*?)(?=\n## |$)", body, re.DOTALL)
```

**Books Library reference:** `BOOKS/books-flashcards.canvas` — 55 books across 5 genre sections (banned, psychology, consciousness, introvert, fiction & philosophy), each card showing cover, title, author, status, rating, and up to 4 key takeaways. Use as a template when generating flashcard canvases from catalog notes.

## Troubleshooting

### `search_files` Returns 0 Results on Windows Vault Paths
`search_files` with paths like `/vault/` containing spaces and special characters
returns zero results even when the string exists in those files. This is a tool limitation on Windows.
**Workaround:** Use `terminal` with `grep` instead:
```bash
cd "/vault" && grep -rl "New Note Title" . --include="*.md" 2>/dev/null
```
Use `grep -rl` (recursive, list filenames only) for verification passes. Use `grep -c` (count per file) for quick checks.

### Verification returns 0 but the wikilink exists
The `search_files` tool returning `0` on Windows vault paths is a false negative. Always verify with the
`terminal` + `grep` workaround above before concluding the patch didn't apply.

## Pitfalls

### Creating without wiring
Writing a note with `write_file` and declaring it "done" is insufficient. The user considers a note incomplete if it is saved but not integrated into the vault's MOC hierarchy and back-link fabric. The user will follow up with "did you link and store it with related data in my second brain??"

Always run all four steps after creating a substantive vault note.

### Patching tail sections without reading the full tail first
`read_file` with offset/limit gets truncated views. Always read the last ~20 lines of the file before patching a `Related Notes` section to ensure you're appending at the right spot.

### Editing auto-generated indexes
`00_FILE_INDEX.md` files generated by Topic Organizer will be regenerated and your manual edits will be lost. Skip them — focus on the MOC files and back-references, which are manually maintained.

### Serially reading dozens of files
When back-referencing 5+ notes, batch the `read_file` calls (read multiple tails in one turn), then batch the `patch` calls. Reading serially one-by-one wastes turns.

### graphify/mempalace setup: AGENTS.md pollution

When running `graphify hermes install` or similar setup commands from non-vault directories, these tools write `AGENTS.md` to the shell's current working directory (often `C:\Users\shrey\`). This pollutes C: with vault-specific rules. Always `cd` to the vault before running setup commands. Delete any stray C: AGENTS.md immediately with `rm`.

### mempalace mine/init: PYTHONPATH poisoning

hermes-agent sets `PYTHONPATH` to its venv, which poisons mempalace's isolated Python environments (chromadb loads wrong numpy ABI). Run mempalace commands with `env -i` or from a clean shell. Vault is already initialized — main ongoing commands are `mempalace mine`, `search`, `wake-up`. Never re-run `mempalace init` on an already-initialized vault.

### Large HTML artifacts: write in one call, never append

For HTML slideshows, write the complete file in a single `write_file` call. Appending via `terminal` or `execute_code` risks partial writes — only the last section appears. Verify with `wc -l` and re-write from scratch if partial.
